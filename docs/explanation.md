## 1. Problem Statement & Motivation

### What is the Problem?

Financial institutions receive **millions of fraud signals every day** — transaction anomalies, watchlist matches, behavioral deviations, and network red flags. Despite this volume, the investigation workflow today is:

- **Manual** — analysts read raw data and write reports by hand.
- **Slow** — a single case can take days or weeks.
- **Expensive** — compliance teams are large and growing.
- **Error-prone** — cognitive load causes inconsistencies across analysts.
- **Hard to audit** — regulators require traceable, evidence-backed reasoning.

### Why Does This Matter?

| Pain Point | Business Impact |
|---|---|
| Manual triage | Large backlogs; high-risk cases missed |
| No structured narrative | Poor regulatory submissions (SAR quality) |
| Siloed data | Analysts miss network-level fraud patterns |
| No audit trail | Failed regulator audits, large fines |
| Slow decisions | Fraudsters move funds before accounts are frozen |

### What is ThreatSight 360?

ThreatSight 360 is an **autonomous, multi-agent investigation system** that:

1. **Receives** a fraud alert (entity + alert type + risk signals).
2. **Triages** the alert using an LLM — deciding if it's a real threat or a false positive.
3. **Gathers** all contextual evidence in parallel (entity profile, transactions, network, watchlists).
4. **Analyses** the evidence across multiple dimensions (network graph, time patterns).
5. **Follows** suspicious leads across connected entities (ownership chains, counterparties).
6. **Generates** a FinCEN-compliant SAR narrative with full evidence citations.
7. **Validates** the narrative quality before presenting it to a human analyst.
8. **Routes** the case to a human reviewer, then **files** the final case to the database.

### When Does ThreatSight 360 Act?

The system acts immediately upon receipt of an alert. An alert can be:
- Triggered by a rule-based engine (e.g., "transaction > $10,000").
- Submitted manually by a compliance analyst.
- Generated by an upstream fraud scoring model.

## 3. Technology Stack Deep Dive

### Why This Stack?

| Component | Technology | Why? |
|---|---|---|
| **Agent Orchestration** | LangGraph (StateGraph) | Enables complex graph-based multi-agent flows with durable persistence, parallel fan-outs, and human-in-the-loop interrupts — impossible with simple chains. |
| **LLM Provider** | Groq (ChatGroq) | Ultra-low latency inference; ideal for investigative tasks that need fast structured output. |
| **LLM Fallback/Embeddings** | AWS Bedrock | Used for high-quality embeddings (voyage-4 via MongoDB AI API) and as a model fallback option. |
| **Agent Framework** | LangChain | Provides tools, structured output binding, and message formatting for agents. |
| **API Framework** | FastAPI (Python) | Async-first, automatic schema docs, supports Server-Sent Events (SSE) for real-time streaming. |
| **Database** | MongoDB Atlas | Flexible document model for heterogeneous entity/transaction schemas; Atlas Search for fuzzy matching; Atlas Vector Search for similarity queries; $graphLookup for network traversal. |
| **Checkpointing** | MongoDBSaver (LangGraph) | Durable persistence of agent state across HTTP requests; enables human-in-the-loop review patterns. |
| **Frontend** | Next.js (App Router) | Server-side rendering, API routes, WebSocket proxy support. |
| **Structured Output** | Pydantic v2 | Schema-validated LLM responses; prevents hallucination leakage into downstream logic. |

## 4. Data Layer — MongoDB Collections & Schema

### What Collections Exist?

| Collection | Purpose |
|---|---|
| `threatsightEntities` | All entities (individuals, organizations, PEPs, shell companies). Holds risk scores, watchlist matches, behavioral embeddings. |
| `transactionsv2` | All financial transactions with `fromEntityId`, `toEntityId`, `amount`, `timestamp`, `riskScore`, `flagged`. |
| `threatsightRelationships` | Directed graph edges between entities (type, strength, confidence). Enables network traversal. |
| `threatsightInvestigations` | Completed investigation case documents — the final output of each pipeline run. |
| `threatsightCheckpoints` | LangGraph checkpoint state — serialized `InvestigationState` snapshots for durability and resume. |
| `threatsightCheckpointWrites` | LangGraph write-ahead log for checkpoint updates. |
| RAG Collections | Policy documents, typology libraries — used by agents via vector search. |

### Why MongoDB?

- The `$graphLookup` aggregation stage lets the Trail Follower recursively traverse ownership chains across `threatsightRelationships` without loading the graph into memory.
- Atlas Vector Search on `profileEmbedding` enables similarity-based entity discovery.
- Flexible document schema accommodates heterogeneous entity types (individual vs. organization vs. shell company).

## 5. Entry Point — Alert Ingestion

### What is an Alert?

An **alert** is the trigger that starts an investigation. It is a JSON payload sent to the AML Backend API:

```json
{
  "entity_id": "ENT-ABC123",
  "alert_type": "high_risk_transaction",
  "alert_description": "Multiple sub-threshold transactions detected",
  "risk_score": 72,
  "flagged_transactions": ["TXN-001", "TXN-002"],
  "watchlist_hits": ["NATIONAL-PEP-RU"]
}
```

### How is the Alert Received?

The `agent_investigation_router` (registered at `/agents/investigations`) exposes a POST endpoint. When called, it:

1. Validates the alert payload.
2. Creates a new LangGraph thread (unique `thread_id`).
3. Calls `get_compiled_graph().astream(...)` with `{"alert_data": alert_payload}`.
4. Streams progress events back to the frontend using **Server-Sent Events (SSE)**.

### When Does Ingestion Happen?

Ingestion is on-demand. An alert is submitted when:
- A rule-based engine detects a threshold breach.
- A compliance analyst manually flags an entity.
- A scheduled batch job submits overnight alerts.

## 6. The Investigation Pipeline — LangGraph State Machine

### Why LangGraph?

LangGraph builds a **directed graph of agent nodes** where:
- Each node is a Python function that reads from and writes to a shared `InvestigationState`.
- Nodes can be sequential, parallel (fan-out/fan-in), or conditional (routing via `Command`).
- State is checkpointed to MongoDB after every node, so investigations survive crashes and can be resumed.
- Human-in-the-loop is implemented as `interrupt_before=["human_review"]` — the graph pauses automatically at that node.

### Graph Topology (Visual)

```
START
  │
  ▼
[triage] ──── auto_close? ──────────────────────────► [auto_close] ──► [finalize] ──► END
  │                                                                           ▲
  │ investigate                                                               │
  ▼                                                                           │
[data_gathering] ──────────────────── fan-out ──────────────────────────┐    │
  │  [fetch_entity_profile]                                              │    │
  │  [fetch_transactions]        (parallel)                             │    │
  │  [fetch_network]                                                    │    │
  │  [fetch_watchlist]  ────────────────────────────────────────────────┘    │
  │                                                                           │
  ▼                                                                           │
[assemble_case]  ◄──── (all 4 workers fan-in here)                          │
  │                                                                           │
  ├──────────────► [network_analyst]  (parallel)                            │
  │                        │                                                 │
  ├──────────────► [temporal_analyst] (parallel)                            │
  │                        │                                                 │
  ▼ (both converge)        ▼                                                 │
[trail_follower] ◄─────────────────────────────────────────────────────────┘
  │
  ▼
[dispatch_sub_investigations] ─── fan-out ─────────────────────────────────┐
  │  [mini_investigate: entity_1]                                           │
  │  [mini_investigate: entity_2]   (parallel, up to 3)                    │
  │  [mini_investigate: entity_3]  ─────────────────────────────────────   │
  │                                ◄──────────────────── fan-in ──────────┘
  ▼
[narrative] ──► [validation] ──► passes? ──► [human_review] ──► [finalize] ──► END
                      │
                      └──── fails? ──► [narrative] (retry loop, max 3x)
```

### 6.1 Shared State — `InvestigationState`

**File:** [`state.py`](file:///c:/Users/R%20KARTHIK/Documents/aml-demo-01/fsi-aml-fraud-detection-main/aml-backend/services/agents/state.py)

#### What is it?

A `TypedDict` that acts as the **single source of truth** shared across all agent nodes. Think of it as a whiteboard where every agent reads what previous agents wrote and adds its own findings.

#### Why a Shared State?

In a multi-agent system with parallel execution, you need a well-defined contract for how agents communicate. The state uses **custom reducers** to handle concurrent writes safely:

| Field | Type | Reducer | Purpose |
|---|---|---|---|
| `alert_data` | `dict` | — | The incoming alert; read-only after ingestion |
| `triage_decision` | `dict` | — | Triage agent's risk score and disposition |
| `gathered_data` | `dict` | `_merge_dicts` | Parallel workers merge their results here |
| `case_file` | `dict` | — | 360° entity profile |
| `typology` | `dict` | — | Crime typology classification |
| `network_analysis` | `dict` | — | Graph metrics |
| `temporal_analysis` | `dict` | — | Time-pattern anomalies |
| `trail_analysis` | `dict` | — | Ownership chains + selected leads |
| `sub_investigation_findings` | `dict` | `_merge_dicts` | Parallel mini-investigations merge here |
| `narrative` | `dict` | — | SAR narrative (Introduction, Body, Conclusion) |
| `validation_result` | `dict` | — | QA agent's quality verdict |
| `human_decision` | `dict` | — | Analyst's approve/reject |
| `agent_audit_log` | `list` | `_append_only` | Immutable log — regulators require this |
| `tool_trace_log` | `list` | `_append_only` | Every tool call with input/output/timing |

#### How does `_merge_dicts` enable parallelism?

When 4 data-gathering workers run simultaneously, they all write to `gathered_data`. The `_merge_dicts` reducer shallow-merges their results:
```python
# Worker 1 writes: {"entity_profile": {...}}
# Worker 2 writes: {"transactions": {...}}
# Worker 3 writes: {"network": {...}}
# Worker 4 writes: {"watchlist": {...}}
# Result: {"entity_profile": {...}, "transactions": {...}, "network": {...}, "watchlist": {...}}
```

### 6.2 Agent Node 1: Triage

**File:** [`nodes/triage.py`](file:///c:/Users/R%20KARTHIK/Documents/aml-demo-01/fsi-aml-fraud-detection-main/aml-backend/services/agents/nodes/triage.py)  
**Prompt:** `TRIAGE_SYSTEM` in [`prompts.py`](file:///c:/Users/R KARTHIK/Documents/aml-demo-01/fsi-aml-fraud-detection-main/aml-backend/services/agents/prompts.py)

#### What does it do?

The Triage node is the **first LLM-powered decision maker** in the pipeline. It reads the raw alert and scores it.

#### Why Triage First?

Without triage, every alert — including obvious false positives — would run through the full pipeline (7+ LLM calls, 4 data fetches). At scale, this is prohibitively expensive. Triage eliminates noise upfront.

#### How does it work?

1. Receives `alert_data` from the state.
2. Calls the LLM with `TRIAGE_SYSTEM` prompt + raw alert JSON.
3. LLM returns a **structured `TriageDecision`** object via `with_structured_output(TriageDecision)`.
4. Uses LangGraph's `Command(goto=...)` to **dynamically route** the pipeline:
   - `risk_score < 25` + no watchlist hits + no flagged transactions → `goto="auto_close"`
   - Otherwise → `goto="data_gathering"`

#### Structured Output — `TriageDecision`:

```python
class TriageDecision(BaseModel):
    risk_score: float       # 0-100 composite risk
    disposition: Literal["auto_close", "investigate"]
    reasoning: str          # Explanation for the decision
    typology_hint: str      # Suspected crime type (e.g., "structuring")
```

#### When does auto_close trigger?

Auto-close is triggered when all of the following are true:
- `risk_score < 25`
- No watchlist hits in the alert
- No flagged transactions
- Entity is classified as low-risk with clean history

Auto-closed cases still pass through `finalize_node` to be persisted with `status="closed_false_positive"`.

### 6.3 Agent Node 2: Data Gathering (Parallel Fan-Out)

**File:** [`nodes/data_gatherer.py`](file:///c:/Users/R%20KARTHIK/Documents/aml-demo-01/fsi-aml-fraud-detection-main/aml-backend/services/agents/nodes/data_gatherer.py)

#### What does it do?

This stage **fans out 4 parallel data-fetch workers** that simultaneously collect all evidence about the suspect entity from MongoDB.

#### Why Parallel?

If each fetch took 500ms and they ran sequentially, data gathering would take 2 seconds minimum. Running them in parallel keeps total time near the slowest single call (~500ms).

#### How does the Fan-Out work?

The `dispatch_data_tasks` dispatcher uses LangGraph's `Send` primitive:

```python
return Command(
    goto=[
        Send("fetch_entity_profile", {"task": "fetch_entity_profile", "entity_id": entity_id}),
        Send("fetch_transactions",   {"task": "fetch_transactions",   "entity_id": entity_id}),
        Send("fetch_network",        {"task": "fetch_network",        "entity_id": entity_id}),
        Send("fetch_watchlist",      {"task": "fetch_watchlist",      "entity_id": entity_id}),
    ]
)
```

Each `Send` spawns an independent node execution with its own state slice.

#### What Does Each Worker Fetch?

| Worker | Tool Called | Data Retrieved |
|---|---|---|
| `fetch_entity_profile` | `get_entity_profile` | Name, type, risk score, risk level, addresses, identity documents |
| `fetch_transactions` | `query_entity_transactions` | Last 50 transactions, flagged amounts, counterparties |
| `fetch_network` | `analyze_entity_network` | 2-hop relationship graph, high-risk connections, shell indicators |
| `fetch_watchlist` | `screen_watchlists` | Sanctions hits, PEP matches, adverse media |

#### Fan-In: `assemble_case_node`

All 4 workers write their results to `gathered_data` via the `_merge_dicts` reducer. When all 4 complete, LangGraph automatically proceeds to `assemble_case` because all 4 edges terminate there:

```python
builder.add_edge("fetch_entity_profile", "assemble_case")
builder.add_edge("fetch_transactions",   "assemble_case")
builder.add_edge("fetch_network",        "assemble_case")
builder.add_edge("fetch_watchlist",      "assemble_case")
```

### 6.4 Agent Node 3: Case Assembly + Typology Classification

**File:** [`nodes/data_gatherer.py`](file:///c:/Users/R%20KARTHIK/Documents/aml-demo-01/fsi-aml-fraud-detection-main/aml-backend/services/agents/nodes/data_gatherer.py) → `assemble_case_node`  
**Prompt:** `CASE_ASSEMBLY_SYSTEM` in [`prompts.py`](file:///c:/Users/R KARTHIK/Documents/aml-demo-01/fsi-aml-fraud-detection-main/aml-backend/services/agents/prompts.py)

#### What does it do?

This single LLM call does **two things simultaneously**:
1. **Synthesises** all gathered evidence into a structured `CaseFile` (360° entity profile).
2. **Classifies** the crime typology (`CrimeTypology` enum) with confidence and red flags.

#### Why Combine Both in One LLM Call?

Case assembly and typology classification require the same evidence context. Splitting them into two calls would double latency and token cost for no benefit.

#### How does Typology Classification work?

Before the LLM call, the agent **optionally searches the typology library** using RAG:
```python
if hint:  # typology_hint from triage
    relevant_typologies = search_typologies.invoke({"query": hint})
    typology_context = truncate_payload({"typologies": relevant_typologies}, max_chars=4000)
```

This grounds the LLM in actual regulatory typology definitions (e.g., what "structuring" means per FinCEN guidelines) rather than relying on the model's training data alone.

#### Available Typologies:

```python
class CrimeTypology(str, Enum):
    STRUCTURING         = "structuring"          # Sub-threshold splits
    LAYERING            = "layering"             # Complex movement to obscure origin
    FUNNEL_ACCOUNT      = "funnel_account"       # Aggregation point for dirty money
    TRADE_BASED_ML      = "trade_based_money_laundering"
    TERRORIST_FINANCING = "terrorist_financing"
    FRAUD_SCHEME        = "fraud_scheme"
    SANCTIONS_EVASION   = "sanctions_evasion"
    CRYPTO_MIXING       = "crypto_mixing"
    ELDER_EXPLOITATION  = "elder_exploitation"
    SHELL_COMPANY       = "shell_company"
    PEP_ABUSE           = "pep_abuse"
    UNKNOWN             = "unknown"
```

#### Output — `CaseAssemblyOutput`:

```python
class CaseAssemblyOutput(BaseModel):
    case_file: CaseFile        # 360° profile
    typology: TypologyResult   # Classification with confidence + red flags
```

### 6.5 Agent Node 4a: Network Analyst (Parallel)

**File:** [`nodes/network_analyst.py`](file:///c:/Users/R%20KARTHIK/Documents/aml-demo-01/fsi-aml-fraud-detection-main/aml-backend/services/agents/nodes/network_analyst.py)

#### What does it do?

A **pure compute node (no LLM)** that calculates graph-theoretic risk metrics from the entity's relationship network stored in MongoDB.

#### Why No LLM Here?

Network metrics (degree centrality, risk propagation) are deterministic mathematical computations. Using an LLM for this would be slower, more expensive, and less accurate. The LLM is reserved for reasoning tasks.

#### How does it work?

| Metric | Calculation | Interpretation |
|---|---|---|
| `degree_centrality` | `(in_degree + out_degree) / (2 × (N-1))` | > 0.5 → hub entity (many connections) |
| `network_risk_score` | `base_risk + (weighted_connection_risk × 0.3)` | Composite of entity + neighbor risk |
| `base_entity_risk` | From `riskAssessment.overall.score` in MongoDB | Own risk score |
| `high_risk_connections` | Count from network data | Direct suspicious links |
| `shell_structure_indicators` | From network data | Nominee directors, circular ownership |

#### When is it Executed?

It runs **in parallel with `temporal_analyst`** immediately after `assemble_case`. Both write to different state keys (`network_analysis` vs `temporal_analysis`) so there are no conflicts.

### 6.6 Agent Node 4b: Temporal Analyst (Parallel)

**File:** [`nodes/temporal_analyst.py`](file:///c:/Users/R%20KARTHIK/Documents/aml-demo-01/fsi-aml-fraud-detection-main/aml-backend/services/agents/nodes/temporal_analyst.py)

#### What does it do?

Another **pure compute node (no LLM)** that detects time-based suspicious patterns in the entity's transaction history using MongoDB aggregation pipelines.

#### Why MongoDB Aggregation Instead of Python?

MongoDB aggregation pushes the computation to the database layer, which is optimized for this. Loading all transactions into Python memory would be slower and memory-intensive.

#### What Patterns are Detected?

| Pattern | Detection Method | Red Flag |
|---|---|---|
| **Structuring** | Transactions ≥ $8,000 and < $10,000, grouped by day, ≥ 2 on same day | Breaking up large amounts to avoid reporting thresholds |
| **Velocity Anomalies** | Weekly transaction counts vs. baseline average; z-score > 2.0 | Sudden spikes in activity |
| **Round-Trip Flows** | Money sent to entity X, then received back from X within 30 days | Layering / wash trading |
| **Time Anomalies** | Percentage of transactions outside business hours or on weekends | Unusual operational patterns |
| **Dormancy Bursts** | Gap > 30 days of no activity, followed by high-volume burst | Account reactivation for fraud |

#### How are Results Used?

The `TemporalAnalysis` output feeds into:
- `trail_follower` for lead prioritization.
- `narrative` as evidence for the SAR body.
- `validation` to check if the narrative addressed temporal evidence.

### 6.7 Agent Node 5: Trail Follower

**File:** [`nodes/trail_follower.py`](file:///c:/Users/R%20KARTHIK/Documents/aml-demo-01/fsi-aml-fraud-detection-main/aml-backend/services/agents/nodes/trail_follower.py)  
**Prompt:** `TRAIL_FOLLOWER_SYSTEM` in [`prompts.py`](file:///c:/Users/R KARTHIK/Documents/aml-demo-01/fsi-aml-fraud-detection-main/aml-backend/services/agents/prompts.py)

#### What does it do?

The Trail Follower is a **reasoning agent** that:
1. Uses MongoDB `$graphLookup` to recursively trace **ownership chains** (up to 3 hops) from the subject entity.
2. Combines network analysis + temporal analysis + ownership chains.
3. Asks the LLM to **select up to 3 leads** (connected entities) most likely involved in the crime.

#### Why is This Important?

Financial crimes rarely involve a single entity. Shell companies, nominee directors, and counterparties form layered structures. The Trail Follower is what allows ThreatSight to **follow the money** beyond the directly flagged entity.

#### How does `$graphLookup` work here?

```python
{
    "$graphLookup": {
        "from": "threatsightRelationships",
        "startWith": "$target.entityId",
        "connectFromField": "target.entityId",
        "connectToField": "source.entityId",
        "as": "chain",
        "maxDepth": 2,               # 3 total hops (1 direct + 2 via graphLookup)
        "restrictSearchWithMatch": {
            "type": {"$in": OWNERSHIP_TYPES}  # Only ownership/control relationships
        }
    }
}
```

This follows chains of: `owns → controls → ubo_of → parent_of_subsidiary → nominee_director` etc.

#### When is the LLM Skip Triggered?

If `network_size <= 2` AND `high_risk_connections == 0` AND `ownership_chains == []`, the LLM call is **skipped entirely**. The agent returns `"trail_analysis_skipped"` to avoid wasting tokens on entities with no meaningful network.

#### Lead Selection Output — `TrailAnalysis`:

```python
class TrailAnalysis(BaseModel):
    ownership_chains: List[dict]         # Raw chains from $graphLookup
    shell_patterns:   List[str]          # Identified shell structures
    leads:            List[InvestigationLead]  # Selected leads (up to 3)
    summary:          str
```

Each `InvestigationLead` specifies an `entity_id`, `priority` (high/medium/low), `reason`, and `risk_indicators`.

### 6.8 Agent Node 6: Sub-Investigator (Parallel Fan-Out)

**File:** [`nodes/sub_investigator.py`](file:///c:/Users/R%20KARTHIK/Documents/aml-demo-01/fsi-aml-fraud-detection-main/aml-backend/services/agents/nodes/sub_investigator.py)  
**Prompt:** `LEAD_ASSESSMENT_SYSTEM` in [`prompts.py`](file:///c:/Users/R KARTHIK/Documents/aml-demo-01/fsi-aml-fraud-detection-main/aml-backend/services/agents/prompts.py)

#### What does it do?

For each lead selected by the Trail Follower, this spawns a **self-contained mini-investigation** that runs in parallel. Each mini-investigation:

1. Fetches full entity profile, watchlist, transactions, and 1-hop network for the lead entity.
2. Presents the evidence plus parent investigation context to the LLM.
3. Produces a `LeadAssessment` with risk level, key findings, and recommendation.

#### Why Parallel Again?

Up to 3 leads can be investigated simultaneously. Running them in parallel keeps total sub-investigation time at ~1× (not 3×) the duration of a single mini-investigation.

#### How does the Fan-Out work?

Same `Send`-based pattern as data gathering:

```python
for lead in leads[:3]:
    send_targets.append(
        Send("mini_investigate", {
            "entity_id": lead.entity_id,
            "reason": lead.reason,
            "parent_context": {...}
        })
    )
```

Each `mini_investigate` worker writes to `sub_investigation_findings[entity_id]` which merges via `_merge_dicts`.

#### Output — `LeadAssessment`:

```python
class LeadAssessment(BaseModel):
    entity_id:              str
    risk_level:             Literal["low", "medium", "high", "critical"]
    risk_score:             float
    connection_to_subject:  str
    key_findings:           List[str]
    red_flags:              List[str]
    recommendation:         Literal["no_concern", "monitor", "escalate", "investigate_further"]
    summary:                str
```

### 6.9 Agent Node 7: Narrative (SAR Writer)

**File:** [`nodes/narrative.py`](file:///c:/Users/R%20KARTHIK/Documents/aml-demo-01/fsi-aml-fraud-detection-main/aml-backend/services/agents/nodes/narrative.py)  
**Prompt:** `NARRATIVE_SYSTEM` in [`prompts.py`](file:///c:/Users/R KARTHIK/Documents/aml-demo-01/fsi-aml-fraud-detection-main/aml-backend/services/agents/prompts.py)

#### What does it do?

The most complex LLM prompt in the system. The SAR Writer agent generates a **FinCEN-compliant Suspicious Activity Report (SAR) narrative** — the formal written justification required by US regulators for any SAR filing.

#### Why is SAR Narrative Generation So Difficult?

A SAR narrative must:
- Follow the **who/what/when/where/why/how** structure mandated by FinCEN.
- Cite every claim with specific evidence (transaction IDs, entity IDs, amounts).
- Avoid fabricating any details.
- Be 2,000–4,000 characters — neither too brief nor excessively verbose.
- Cover all 9 evidence sections: entity profile, transactions, sanctions, adverse media, typology, network, temporal, trail, and sub-investigations.

#### How does the Agent Avoid Hallucination?

The prompt provides:
1. **Mandatory evidence checklist** — 9 sections the narrative MUST address.
2. **Citation rules** — every claim must use a specific tag format: `[transaction:TXN-ID]`, `[watchlist:LIST-NAME]`, etc.
3. **Anti-fabrication rules** — relationship "strength" must not be presented as ownership percentage.
4. **Entity context rules** — off-hours activity must be interpreted in the context of entity type (a multinational corporation may legitimately transact at night).

#### Revision Loop

If the validation agent rejects the narrative, the Narrative node **re-runs with revision context**:

```python
if needs_revision:
    parts = ["REVISION REQUIRED — the previous draft had these quality issues:"]
    parts.extend(f"- {issue}" for issue in all_issues)
    # Appended to the next LLM call
```

#### Output — `SARNarrative`:

```python
class SARNarrative(BaseModel):
    introduction:    str   # Reason for filing, entity summary, risk level
    body:            str   # Chronological detail covering all 9 evidence sections
    conclusion:      str   # Actions taken, data gaps, supporting documents
    cited_evidence:  List[str]  # All citation tags used
```

### 6.10 Agent Node 8: Validation (QA Agent)

**File:** [`nodes/validator.py`](file:///c:/Users/R%20KARTHIK/Documents/aml-demo-01/fsi-aml-fraud-detection-main/aml-backend/services/agents/nodes/validator.py)  
**Prompt:** `VALIDATION_SYSTEM` in [`prompts.py`](file:///c:/Users/R KARTHIK/Documents/aml-demo-01/fsi-aml-fraud-detection-main/aml-backend/services/agents/prompts.py)

#### What does it do?

An LLM-powered **Quality Assurance agent** that reviews the SAR narrative against all evidence and either approves it (routes to `human_review`) or rejects it (routes back to `narrative` for revision).

#### Why a Separate Validation Agent?

The SAR Writer agent cannot reliably self-critique its own output. A separate QA agent with a fresh context window and a checklist-based prompt is more reliable at catching errors.

#### What Does the Validator Check?

| Check | What it Looks For |
|---|---|
| **Completeness** | All 3 sections (Intro, Body, Conclusion) present; all 9 evidence sections addressed |
| **Factual accuracy** | Every claim traceable to provided evidence sections |
| **Mathematical consistency** | Totals, counts, percentages don't contradict source data |
| **Missing data acknowledgment** | Evidence gaps explicitly stated (not silently omitted) |
| **Citation quality** | Proper citation tags; no truncated IDs like `[transaction:TXN-xxx...]` |
| **No fabrication** | No entity IDs, amounts, or scores not present in evidence |
| **Regulatory compliance** | Meets FinCEN SAR format requirements; appropriate length |

#### Routing Decisions:

| Route | Trigger |
|---|---|
| `human_review` | Narrative passes all quality checks — ready for analyst approval |
| `narrative` | Narrative has fixable issues — re-draft required |
| `data_gathering` | Critical evidence is missing — re-collect data (rare) |
| `finalize` | Auto-finalize (only for trivial false positive cases) |

#### How Many Times Can Narrative Retry?

The state tracks `validation_count`. The system allows a maximum of **3 validation loops** before escalating regardless of quality, to prevent infinite loops.

#### Output — `ValidationResult`:

```python
class ValidationResult(BaseModel):
    is_valid:       bool
    score:          float          # Quality score 0-100
    issues:         List[str]      # Flagged problems
    missing_data:   List[str]      # Evidence gaps
    factual_errors: List[str]      # Specific fabrications found
    route_to:       Literal["data_gathering", "narrative", "human_review", "finalize"]
```

### 6.11 Agent Node 9: Human Review (Interrupt Gate)

**File:** [`nodes/human_review.py`](file:///c:/Users/R%20KARTHIK/Documents/aml-demo-01/fsi-aml-fraud-detection-main/aml-backend/services/agents/nodes/human_review.py)

#### What does it do?

This is the **human-in-the-loop checkpoint**. The graph pauses execution here, waiting for a compliance analyst to review the AI-generated SAR narrative and make a final decision.

#### Why Human Review?

- Regulatory requirement: SAR filings are legal documents; a human must authorize them.
- AI quality assurance: The validator catches most issues, but humans provide the final check.
- Contextual judgment: An analyst may know context the AI cannot access (e.g., prior oral communications with the client).

#### How is it Implemented?

The graph is compiled with:
```python
_compiled_graph = builder.compile(
    checkpointer=checkpointer,
    interrupt_before=["human_review"],  # ← Pause here automatically
)
```

When the pipeline reaches `human_review`, LangGraph:
1. Saves the full `InvestigationState` to MongoDB (`threatsightCheckpoints`).
2. Returns control to the API caller with `status="pending_human_review"`.
3. The frontend displays the investigation + narrative to the analyst.

When the analyst submits their decision, the API resumes the graph using the saved `thread_id`:
```python
graph.astream({"human_decision": {...}}, config={"thread_id": thread_id})
```

## 7. Conversational Chat Agent — ThreatSight Co-Pilot

ReAct (Reasoning + Acting) agents interleave:
- **Thought** — what tool should I use and why?

This lets the agent chain multiple tools intelligently (e.g., "find entity → check watchlist → trace fund flow").

## 9. LLM Configuration & Reliability

**File:** [`services/agents/llm.py`](file:///c:/Users/R%20KARTHIK/Documents/aml-demo-01/fsi-aml-fraud-detection-main/aml-backend/services/agents/llm.py)

### What LLM is Used?

The system uses **Groq-hosted models** via `langchain_groq.ChatGroq`. The model is configured via environment variable:

```bash
LLM_MODEL_NAME=openai/gpt-oss-120b   # Default
```

Temperature is set to `0.1` — near-deterministic to prevent creative hallucinations in compliance-sensitive outputs.

### Why Groq?

Groq's LPU (Language Processing Unit) delivers extremely low inference latency. For an investigation pipeline that chains 8+ LLM calls, latency compounds quickly. Groq reduces per-call latency from seconds to hundreds of milliseconds.

### How is the LLM a Singleton?

```python
_llm_instance: ChatGroq | None = None

def get_llm() -> ChatGroq:
    global _llm_instance
    if _llm_instance is None:
        _llm_instance = ChatGroq(model=_MODEL_NAME, temperature=0.1, ...)
    return _llm_instance
```

The singleton avoids creating a new HTTP connection pool on every agent node invocation.

### Retry Logic

The `invoke_with_retry` decorator uses **exponential backoff** with up to 3 attempts:

```python
@retry(
    retry=retry_if_exception(_is_retryable),
    stop=stop_after_attempt(3),
    wait=wait_exponential(multiplier=1, min=2, max=15),
)
def invoke_with_retry(llm, messages):
    return llm.invoke(messages)
```

Retryable exceptions include: `ThrottlingException`, `ServiceUnavailableException`, `ModelTimeoutException`, `TooManyRequestsException`.

## 14. End-to-End Flow: Alert to Filed SAR

This section traces a **complete investigation lifecycle** for a suspicious entity.

### Scenario: Structuring Alert

An entity (`ENT-CORP-007`) triggers an alert:
- 5 transactions just below $10,000 within 3 days.
- Counterparty appears on a PEP watchlist.
- Risk score: 68.

---

**Step 1: Alert Ingestion**
- POST to `/agents/investigations/` with `{"entity_id": "ENT-CORP-007", "alert_type": "structuring", ...}`.
- LangGraph creates thread `thread-abc123`, initializes `InvestigationState`.

**Step 2: Triage Node** _(~800ms, 1 LLM call)_
- LLM evaluates alert: `risk_score=68`, `disposition="investigate"`, `typology_hint="structuring"`.
- Routes to `data_gathering`.

**Step 3: Data Gathering Fan-Out** _(~600ms, 4 parallel DB calls)_
- `fetch_entity_profile` → entity is a private limited company, risk=68.
- `fetch_transactions` → 28 total transactions, 5 flagged, structuring window detected.
- `fetch_network` → 12 connected entities, 3 high-risk, shell indicators present.
- `fetch_watchlist` → PEP match on counterparty, confidence=0.87.

**Step 4: Case Assembly + Typology** _(~1200ms, 1 LLM call)_
- RAG retrieves "structuring" typology definition.
- LLM classifies: `primary_typology="structuring"`, `confidence=0.85`, `red_flags=["sub-threshold clustering", "same-day patterns", "PEP counterparty"]`.
- Case file assembled with all 9 fields.

**Step 5a: Network Analyst** _(~200ms, no LLM)_
- `degree_centrality=0.41`, `network_risk_score=74.3`, `high_risk_connections=3`.

**Step 5b: Temporal Analyst** _(~250ms, no LLM)_
- 2 structuring windows detected (3 txns/day, $8,400–$9,800 range).
- Velocity z-score=2.8 (spike week of August 20).
- No round-trips, no dormancy burst.

**Step 6: Trail Follower** _(~900ms, 1 LLM call)_
- `$graphLookup` traces 2 ownership chains (entity → shell1 → UBO).
- LLM selects 2 leads: `shell1` (high priority — nominee director), `UBO-PEP` (high priority — PEP connection).

**Step 7: Sub-Investigations** _(~1400ms, 2 parallel LLM calls)_
- `mini_investigate:shell1` → `risk_level="high"`, `recommendation="investigate_further"`.
- `mini_investigate:UBO-PEP` → `risk_level="critical"`, `recommendation="escalate"` (multiple watchlist hits).

**Step 8: Narrative Generation** _(~2000ms, 1 LLM call)_
- SAR Writer generates Introduction + Body + Conclusion.
- 3,400 characters with 18 citation tags.

**Step 9: Validation** _(~1100ms, 1 LLM call)_
- QA agent scores: 91/100. Issues: 1 minor (temporal anomaly not mentioned explicitly).
- Narrative node re-runs with revision context.
- Second pass: 96/100. Routes to `human_review`.

**Step 10: Human Review** _(graph pauses)_
- Frontend shows investigation to analyst with narrative and evidence tabs.
- Analyst reviews, adds notes, clicks **Approve**.
- API resumes graph with `{"human_decision": {"decision": "approve", "analyst_id": "..."}}`.

**Step 11: Finalize** _(~150ms, no LLM)_
- Case document assembled with all pipeline outputs.
- Written to `threatsightInvestigations` with `status="filed"`.
- Pipeline metrics: 8 LLM calls, 23 tool calls, ~8.5 seconds total.

## 15. Key Design Decisions & Trade-Offs

### Decision 1: LangGraph over Custom Orchestration

**What:** Using LangGraph's `StateGraph` instead of writing a custom orchestrator.

**Why:** LangGraph provides:
- Durable state checkpointing out of the box (critical for human-in-the-loop).
- Built-in parallel execution via `Send`.
- Graph-level persistence to MongoDB.
- Interrupt/resume semantics for human review.

**Trade-off:** LangGraph adds complexity and a learning curve. Simple sequential pipelines would be easier to write as plain Python.

---

### Decision 2: Pure-Compute Nodes for Network and Temporal Analysis

**What:** `network_analyst` and `temporal_analyst` use MongoDB aggregation instead of LLM reasoning.

**Why:** These computations are deterministic, mathematical, and MongoDB-native. An LLM would be slower, more expensive, and less precise for tasks like "calculate z-score of weekly transaction velocity."

**Trade-off:** Less flexibility — the patterns detected are fixed by the code, not emergent from LLM reasoning.

---

### Decision 3: Single LLM Call for Case Assembly + Typology

**What:** Combining two tasks (case file synthesis + typology classification) into one LLM call.

**Why:** Both tasks require the same evidence context. Splitting doubles latency and token cost.

**Trade-off:** The combined prompt is large and complex; harder to debug if the typology classification is wrong.

---

### Decision 4: `interrupt_before=["human_review"]` for HITL

**What:** The graph pauses automatically before `human_review` without any application-level pause logic.

**Why:** LangGraph's checkpointing model handles the pause/resume transparently. State is persisted in MongoDB. The API can return immediately, and analysts can review the case at their own pace — even hours later.

**Trade-off:** Requires a stateful backend (MongoDB); stateless deployments would not support this.

---

### Decision 5: Append-Only Audit Log

**What:** The `_append_only` reducer prevents any node from removing or modifying existing audit entries.

**Why:** Regulatory compliance requires tamper-evident logs. If an agent could overwrite earlier entries, the audit trail would be unreliable.

**Trade-off:** State size grows with each pipeline stage; needs truncation strategy for long-running investigations.

| **Checkpointing** | Persisting agent state to storage so pipelines can be paused and resumed. |
| **Fan-Out** | Dispatching multiple parallel tasks from a single orchestrator node. |
| **Fan-In** | Collecting results from parallel workers back into a single aggregation node. |
